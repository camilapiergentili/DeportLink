# Loop: F16 — `AddScheduleUseCase` sin lock ni constraint permite duplicar horarios de una cancha/día y romper la disponibilidad/reserva de esa cancha con un 500 persistente

## Metadata

- **Auditoría de origen:** docs/software-review-2026-08-31.md (sección Findings, `### F16`, líneas ~131-155)

## Related findings
- `RELATED_FINDING` (sin ID propio todavía — no viene de ningún reporte previo, se encontró durante el
  ANALYZE de este loop): **`filterConflicts()` en `AddScheduleUseCase.java:79-89` no impide, ni siquiera en
  ausencia total de concurrencia, que dos altas de horario *secuenciales* (dos requests HTTP separados, uno
  después de que el otro ya commiteó) inserten dos filas de `availability` para el mismo `(court_id,
  day_of_week)`, siempre que los rangos horarios no se solapen** (ej.: alta de "Lunes 8–12", y más tarde,
  sin ninguna carrera de por medio, alta de "Lunes 14–18" para la misma cancha). El chequeo solo rechaza
  solapamiento de horario, no la existencia de una fila previa para ese mismo día. Como
  `ScheduleRepositoryPort.findByCourtIdAndDay` (usado por `GetScheduleByDayUseCase`,
  `GetAvailableSlotsUseCase`, `BookReservationUseCase`, `RescheduleReservationUseCase`) asume que existe
  como mucho una fila por `(court, day)`, esta secuencia — sin ninguna carrera — produce el mismo síntoma
  de 500 que describe F16, por una causa distinta y más amplia (un gap de validación de negocio, no de
  concurrencia). Ver razonamiento completo en el ANALYZE de la Iteración 1. **Deliberadamente no se toca
  en este loop** — cerrarlo bien requiere una decisión de producto (¿las canchas pueden tener horarios
  partidos —mañana/tarde— el mismo día, o el invariante real es "un horario por cancha y día"?) que no le
  corresponde a este loop resolver. Queda para que un humano lo triage y, si corresponde, se audite con
  `software-review` para que reciba un ID propio.

## Iteración 1

### ANALYZE

**ANALYSIS RESULT**

- **Root cause:** `AddScheduleUseCase.execute()` (`AddScheduleUseCase.java:32-57`) hace un check-then-act
  sin lock: lee las canchas/horarios existentes con `scheduleRepository.findAllByCourtId(courtId)`
  (línea 52), decide en memoria de aplicación qué horarios nuevos no solapan con los existentes
  (`filterConflicts`, líneas 79-89), y recién después persiste con `scheduleRepository.saveAll(unique)`
  (línea 55). No hay ninguna operación que bloquee la fila de `Court` (ni ninguna otra) antes de esa
  lectura — a diferencia del resto de las mutaciones de este mismo dominio (ver "Existing protection"
  abajo). La tabla `availability` (`V1__baseline.sql:109-118`) no tiene ningún `UNIQUE` sobre
  `(court_id, day_of_week)`, solo un índice no-único (`idx_availability_court_day`).

- **Affected flow (re-trazado en el código actual — este branch se cortó de `development` @ `9a5e365`,
  idéntico al código auditado en `docs/software-review-2026-08-31.md`, confirmado con
  `git diff development fix/f1-login-rate-limiter-proxy-ip -- src pom.xml` vacío antes de cortar la
  rama):**
  - Entry point: `POST /api/schedules/court/{idCourt}` (`ScheduleController.java:30-42`), alcanzable por
    `hasRole('ADMIN')` o `@courtAuthorization.isOwnerOfCourt(#idCourt, authentication)` — el propio dueño
    de la cancha puede dispararlo, no hace falta un segundo actor.
  - `AddScheduleUseCase.execute()` → (carrera) → dos filas `ScheduleEntity` para el mismo
    `(court_id, day_of_week)` en `availability`.
  - `ScheduleRepository.findByCourtIdAndDay(long, DayOfWeek)` (`ScheduleRepository.java:26`) — derived
    query que devuelve `Optional<ScheduleEntity>`; Spring Data la genera esperando 0 o 1 resultado.
  - Consumida por `ScheduleGatewayAdapter.findByCourtAndDay()` (`ScheduleGatewayAdapter.java:18-21`) y
    directamente por `ScheduleRepositoryPort.findByCourtIdAndDay` a través de
    `GetScheduleByDayUseCase.execute()` (`GetScheduleByDayUseCase.java:16-19`).
  - Tres casos de uso más consumen la versión del gateway: `GetAvailableSlotsUseCase.execute()`
    (`GetAvailableSlotsUseCase.java:37`), `BookReservationUseCase.execute()`
    (`BookReservationUseCase.java:49`) y `RescheduleReservationUseCase.execute()`
    (`RescheduleReservationUseCase.java:77`).
  - Con 2 filas para el mismo `(court, day)`, cualquiera de esas cuatro llamadas dispara
    `IncorrectResultSizeDataAccessException` (JPA `NonUniqueResultException` por debajo) — no es
    `BusinessException` ni `DataIntegrityViolationException`, así que cae en
    `GlobalExceptionHandler.handleGenericException()` (`@ExceptionHandler(Exception.class)`) → **500**,
    con el stack trace solo en el log del servidor (`log.error("Unexpected error: {}", ...)`) y
    `"Ocurrió un error inesperado"` para el cliente.

- **Existing protection:** ninguna dentro de `AddScheduleUseCase`. El proyecto **ya tiene el patrón
  correcto para esta exacta clase de problema**, aplicado a los dos casos de uso hermanos en el mismo
  archivo/paquete: `UpdateScheduleUseCase.execute()` y `DeleteScheduleUseCase.execute()`, corregidos en la
  rama `fix/f4-schedule-concurrency-lock` (commit `06aa2cf`, **no mergeada a `development` todavía** —
  confirmado con `git log development..fix/f4-schedule-concurrency-lock`). Ambos toman
  `courtRepository.findByIdForUpdate(courtId)` (`CourtRepository.java:72-74`,
  `@Lock(PESSIMISTIC_WRITE)`) como **primera operación** de su método `@Transactional`, antes de leer
  cualquier otra cosa — el mismo lock que ya usan `BookReservationUseCase`, `RescheduleReservationUseCase`,
  `DeleteCourtUseCase` y `DeleteBranchUseCase`. `AddScheduleUseCase` quedó fuera de ese fix: `git show
  fix/f4-schedule-concurrency-lock --name-only` solo toca `UpdateScheduleUseCase.java` y
  `DeleteScheduleUseCase.java`, no `AddScheduleUseCase.java`.

- **Missing protection:** `AddScheduleUseCase.execute()` lee `Court` con
  `courtRepository.findById(courtId)` (línea 35-36) — `Optional<Court> findById(Long)`, sin lock — así que
  dos ejecuciones concurrentes para la misma cancha ven ambas el estado de `availability` previo a la
  carrera y pueden pasar `filterConflicts` en paralelo.

- **Confianza:** Confirmado. Mecanismo re-trazado end-to-end por lectura directa en esta misma pasada
  (no asumido del reporte de origen), sobre código verificado idéntico al auditado. Reachability
  confirmada: un solo actor (el Owner dueño de la cancha, o un Admin) puede disparar la carrera con un
  doble submit del mismo formulario — no requiere coordinar dos usuarios ni una ventana de negocio
  especial.

- **Hallazgo adicional durante este ANALYZE, registrado como `RELATED_FINDING` y explícitamente no
  tocado en este loop:** al trazar todos los consumidores de `findByCourtIdAndDay` para confirmar el
  "Affected flow", se verificó qué es lo único que impide que dos filas de `availability` coexistan para
  el mismo `(court, day)` — y la respuesta es: nada, ni siquiera en ausencia de concurrencia.
  `filterConflicts()` (`AddScheduleUseCase.java:79-89`) solo descarta un horario nuevo si **solapa en
  rango horario** con uno existente del mismo día (`overlaps()`, líneas 91-93) — no rechaza un horario
  nuevo simplemente porque el día ya tiene una fila. Dos requests HTTP completamente secuenciales — el
  segundo disparado bastante después de que el primero ya commiteó, sin ninguna carrera — con rangos que
  no se solapan (ej. "Lunes 8–12" y, en otra request posterior, "Lunes 14–18") pasan ambos el chequeo y
  producen igualmente dos filas para el mismo `(court, day)`, con la misma consecuencia (`findByCourtIdAndDay`
  rompe con 500 la próxima vez que alguien consulte disponibilidad ese día). Verificado que ningún otro
  caso de uso ni test en el repo (`GetAllSchedulesByCourtUseCase`, `GetScheduleByDayUseCase`,
  `ConcurrencyTestFixtures`, `ScheduleControllerTest`) ejercita ni documenta "horarios partidos" (mañana/
  tarde) como un escenario soportado — tampoco hay ningún comentario o test que lo contradiga
  explícitamente. Esto es ambiguo por diseño, no por falta de investigación: **cerrarlo bien requiere saber
  si "más de un bloque horario por cancha y día" es una funcionalidad querida** (en cuyo caso el bug real
  está en el lado de lectura, que asume `Optional` de a una fila) **o si el invariante real es "un
  horario por cancha y día"** (en cuyo caso el bug está en `filterConflicts`, que debería rechazar
  cualquier horario nuevo para un día que ya tiene uno, no solo los que solapan). Ninguna lectura de
  código puede resolver esa pregunta — es la condición de parada de ANALYZE para *ese* mecanismo
  específico, aplicada de forma acotada: no bloquea el mecanismo de F16 (la carrera), que sí tiene una
  corrección clara y sin ambigüedad de producto (ver PLAN).

**Decisión de fase:** el mecanismo de F16 (la carrera) está trazado con evidencia concreta y alcanzable, y
tiene un patrón de corrección ya probado en este mismo código para los dos casos de uso hermanos. Se
avanza a `PLAN`. El mecanismo adicional descubierto (gap secuencial de `filterConflicts`) se deja
registrado arriba como `RELATED_FINDING` y no participa de `PLAN`/`IMPLEMENT` de este loop.
