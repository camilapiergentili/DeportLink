- **Confianza:** Alta. Mecanismo simple (ausencia de un límite superior en una anotación), sin condición de carrera ni dependencia de infraestructura externa — no hay ambigüedad que requerir información humana.

### PLAN

**Alternativas comparadas:**

1. **Agregar `@Size(max = 72)` + un `@AssertTrue` que cuente bytes UTF-8 del password, en `UserRequestDto`** (elegida).
   - Ventaja: valida *antes* de llegar al encoder, en la misma capa (Bean Validation) donde ya vive el resto de las reglas de este DTO (`@NotBlank`, `@Email`, `@PasswordMatches`) — consistente con el patrón existente del proyecto, no introduce un mecanismo nuevo.
   - Por qué dos anotaciones y no solo `@Size`: `@Size` cuenta *caracteres* de Java (UTF-16 code units), no bytes. Una contraseña de 72 caracteres con tildes o emojis puede ocupar más de 72 bytes UTF-8 y seguir pasando `@Size(max=72)` sin problema, mientras que BCrypt sí la rechaza. El `@AssertTrue` mide bytes reales y cierra ese hueco. `@Size` se mantiene igual como cota barata de caracteres (falla rápido, mensaje más simple para el caso común ASCII) sin reemplazar al chequeo de bytes.
   - Trade-off aceptado: el límite de 72 queda hardcodeado como constante mágica en el DTO. Es aceptable porque 72 es una propiedad fija del algoritmo BCrypt (no un valor de configuración del proyecto) — no cambia entre entornos ni versiones futuras del encoder mientras se siga usando BCrypt.
2. **Pre-hashear con SHA-256 antes de pasarle el resultado a BCrypt** (descartada, coincide con lo que ya señala el reporte de origen). Elimina el límite de raíz, pero es un cambio de arquitectura criptográfica que invalida todos los hashes ya guardados salvo que se migre progresivamente — desproporcionado para un finding de severidad Media cuyo arreglo real es "agregarle un `max` a una anotación que ya existe".
3. **Capturar `IllegalArgumentException` específicamente en `GlobalExceptionHandler` y mapearla a 400** (descartada). Resuelve el síntoma (el código de status) pero no la causa: la contraseña igual llega sin validar hasta la capa de infraestructura de seguridad, acoplando el manejo de errores de negocio a un detalle de implementación de una librería externa (`IllegalArgumentException` es genérica — capturarla globalmente correría el riesgo de enmascarar otros bugs de programación reales que hoy caen, correctamente, en el handler genérico). Además no sigue el patrón ya establecido del proyecto de validar en el DTO antes de llegar al use case.

**Tests requeridos:**
- Unit/Validator: instanciar `PlayerRequestDto` y `OwnerRequestDto` reales, pasarlas por un `jakarta.validation.Validator` real (no MockMvc), con tres casos por clase: (a) password de exactamente 72 bytes ASCII → válida: `getBytes(UTF_8).length == 72`, sin violaciones sobre `password`; (b) password de 73 bytes ASCII → inválida, violación sobre `password`; (c) password con caracteres no-ASCII (tildes) cuya longitud en *caracteres* es ≤72 pero cuya longitud en *bytes* UTF-8 supera 72 → inválida — este caso es el que demuestra que el `@AssertTrue` hace un trabajo que `@Size` solo no podría hacer.
- HTTP/MockMvc (contrato real del endpoint, extendiendo `PlayerControllerTest` existente): POST a `/api/players` con password de 73 bytes → `status().isBadRequest()` (400, no 500) y `verifyNoInteractions(registerPlayerUseCase)` (la validación corta antes de llegar al use case, igual que el test ya existente para passwords que no matchean).

**Evidencia requerida antes de declarar RESOLVED:** las pruebas de arriba **ejecutadas** (no solo escritas) y en verde, más una corrida de la suite existente de `PlayerControllerTest`/`OwnerControllerTest` sin regresiones. Esto es un bug de lógica pura en anotaciones de validación — no concurrencia, no infraestructura externa — así que evidencia de tests unitarios/MockMvc ejecutados es *sí* suficiente per las reglas de evidencia del skill (a diferencia de un claim de concurrencia, que exigiría infraestructura real).

## Resultado final

**STATUS: RESOLVED**

`UserRequestDto.password` ahora rechaza, con `HTTP 400` y un mensaje de campo claro, cualquier contraseña que exceda los 72 bytes UTF-8 que BCrypt puede procesar — cubriendo tanto el caso simple (>72 caracteres ASCII) como el caso no obvio (≤72 caracteres pero >72 bytes por tildes/emojis), que es justamente el que un `@Size` sin acompañar dejaría pasar. Evidencia: 6 tests de validación (`UserRequestDtoValidationTest`) + 1 test de contrato HTTP (`PlayerControllerTest`) ejecutados y en verde, sin regresión en la suite preexistente de `PlayerControllerTest`/`OwnerControllerTest`. Como el campo vive en la clase base `UserRequestDto`, el fix cubre `POST /api/players` y `POST /api/owners` con el mismo cambio.

Qué queda fuera de este loop: el módulo de instructores (`InstructorRequestDto`), que no existe todavía en `development`; un test MockMvc dedicado sobre `OwnerController` (redundante, ver OUT_OF_SCOPE); la alternativa de pre-hash SHA-256 (descartada por desproporcionada).
